# 本番・デモ・開発の分け方

この文書は運用の提案です。デモ用の公開先やAPI、GitHubの保護設定を新設した状態ではありません。

## 最初は、同じコードから2つの公開先を作る

| 項目   | 本番                             | デモ                               |
| ------ | -------------------------------- | ---------------------------------- |
| 用途   | 生徒・教員が実際に使う           | 説明・操作体験・新機能の画面確認   |
| URL    | 現在のPWAのURLを維持             | 別のCloudflare Pagesプロジェクト   |
| データ | 学校アカウントと正式な作品・履歴 | 架空の作品・架空のサンプルPDF      |
| 接続先 | 本番の認証・API・DB・PDF保存先   | 本番APIには接続しない              |
| 更新   | 確認した版を明示的に公開         | 確認したいブランチやコミットを公開 |

アプリを2つコピーして開発するのではなく、同じリポジトリ・同じコードを使い、ビルド設定と接続先を分ける。本番URLは利用開始後も変えない。

## ブランチと公開する版

- `main`: テストを通した変更を集める。GitHubへの反映と本番への公開は別の操作にする。
- `codex/*` や `feature/*`: 機能ごとの短い作業ブランチ。Pull Requestで差分とテストを確認してから `main` へ入れる。
- 本番公開時は、そのコミットに `v0.1.0` などのタグを付け、公開URL・対応するAPI/DBの変更・戻す版を記録する。タグは実際に公開したコミットへ付ける。
- 長く使う `demo` ブランチに別実装を積み続けない。同じコミットをデモと本番の設定でビルドできる状態を目指す。

本番にまだ出していない変更が `main` にあっても、本番の版は直近の公開タグで特定できる。運用開始後は「GitHubへpushしただけで本番が変わる」構成にしない。

## 今あるサンプル機能の扱い

`VITE_ENABLE_PREVIEW=true` はサンプル画面を有効にする設定であり、データの接続先を分離する設定ではない。現在の開発サーバーにもサンプル画面がある。

デモとして公開する前に、デモ専用ビルドの入口・架空データ・架空PDFを整え、本番のFirebase設定やAPIのサービスバインディングを渡さない構成にする。URLを分けただけのCloudflareプレビューに、本番の接続設定をそのまま付けて「デモ」と呼ばない。

認証や保存などAPIとの結合確認が必要になったら、アクセスを限定した確認環境を追加する。その場合は確認用の認証・DB・PDF保存先も別に用意する。

## 利用開始までと開始後

2026年11月16日の週に利用を始める想定なら、前の週までに次を整える。

1. 公開済みの変更をGitHubへ整理して反映し、型検査・ビルド・主要操作のテストを揃える。
2. 説明用のデモを別URLで用意し、架空データだけで体験できるようにする。
3. 実際の端末と学校アカウントで、ログイン・検索・PDF・オフライン・問い合わせを確認する。
4. 確認したコミットを運用開始版として公開・記録する。

開始直後は不具合修正を優先する。新機能は作業ブランチとデモで確認してからまとめて公開し、問題があれば直前の公開版へ戻す。DBの変更は古いアプリでも動く順序で適用する。

## GitHubで確認するもの

公開先はフロントエンド専用のリポジトリ。本番DBの移行や管理室・APIのコードは管理側のリポジトリで管理し、この公開リポジトリに管理キーや本番PDFを入れない。

GitHub Actionsで整形・型検査・lint・本番ビルド・ブラウザテストを確認する。Cloudflareの公開設定やGitHubのブランチ保護は別途設定し、`main` にPull Requestとチェックを要求する運用へ移行する。
