# 作業・公開手順（AI・人間共通）

新しい作業の開始時、コード変更・DB移行・公開・削除・復旧の前に必ず読む。Codex、ChatGPT、Claudeなど、担当ツールにかかわらず適用する。依頼と矛盾する場合は依頼を優先し、差分を記録する。

## 採用した環境構成

| 用途 | URL | データ・API |
| --- | --- | --- |
| 本番 | https://kenryo-tankyu-archive.pages.dev | 正式データ・既存API |
| 先行確認版（デモ） | https://demo.kenryo-tankyu-archive.pages.dev | 本番と同じ正式データ・既存API |

同じCloudflare Pagesプロジェクト `kenryo-tankyu-archive` のproductionとpreviewを使う。デモは `demo` の公開エイリアスを使う。同じコードから作り、別実装を長期間維持しない。公開時の `--branch demo` は配信先の指定であり、Gitで長期のdemoブランチを管理する必要はない。

デモは実データを使う先行確認版。お気に入り・履歴・コレクション・問い合わせ・削除なども実データへ反映される。デモだからという理由で試験投稿・削除・通知配信を行わない。書き込みテストは依頼の範囲と対象を確認し、専用の試験アカウント等を使う。認証・認可は本番と同じ。架空サンプルを有効にする `VITE_ENABLE_PREVIEW` はfalseのままとする。

## 作業開始時

1. この文書と、作業する場所のAGENTS.md・CLAUDE.md・READMEを読む。
2. Gitの状態、現在のブランチ、未コミット変更、実際に公開中の版を確認する。他の作業の変更を巻き戻さない。
3. UIだけの変更か、共有API・DB・認証・PDF保存先に影響するかを判定する。共有側の変更はデモだけでなく本番にも即座に影響する。
4. 短い `codex/*` 等の作業ブランチで変更する。公開リポジトリには管理キー、実PDF、ログ、認証情報を入れない。

## 通常の変更と公開

1. 変更に対応する型検査・lint・ビルド・ブラウザテストを実行する。見た目の変更は実画面を確認する。
2. 同じアプリソース・本番用の公開設定からビルドし、まずPages previewのdemoへ公開する。本番productionを上書きしない。
3. デモURLでログイン入口、学校アカウント認証、検索、PDF、狭い画面、オフライン・更新動作を変更範囲に応じて確認する。認証を突破したことにして検証済みと書かない。
4. GitHub PRで差分とチェックを確認してmainへ取り込む。GitHubへのpushと本番への公開は別操作。
5. 本番公開はユーザーの依頼・継続する許可の範囲で行う。確認済みと同じ成果物を公開し、公開後の確認を行う。
6. 日時、ソースコミット、配信ID・URL、API/DBの変更、テスト結果、直前の復元可能な版を公開記録へ残す。本番へ実際に公開したコミットだけにリリースタグを付ける。

管理側ワークスペースでは `scripts/release/deploy-demo.mjs` がデモのビルド・公開を行う。事前にCloudflareへログインし、既存のFirebase公開設定を用意する。公開値以外の秘密情報をappへ渡さない。認証許可ドメインとPages previewのAPIサービスバインディングも必要。APIのOrigin制限をワイルドカードへ緩めない。

## API・DB変更の必須手順

本番とデモは同じAPI・DB。デモへの公開でDBの変更が隔離されるわけではない。

1. 原則は追加→移行→切り替え→削除。新しい列・テーブルを先に追加し、古いアプリが引き続き動くようにする。
2. 必要な期間はAPIが旧・新の両形式を扱い、データの移行・整合性を確認する。書き込みが並行する場合は移行中の更新も欠落させない。
3. 大きな構造変更や破壊的な移行は、そのときだけ別の検証DBでリハーサルする。復元方法を確認し、必要なバックアップを取得する。
4. デモで確認してから新しいアプリを本番へ公開する。
5. 更新ボタンを必須にしていても、古いタブ・オフライン端末・切り替え失敗を考慮する。最低バージョンをAPIで拒否する仕組みが実装済みか、必ずコードで確認する。現時点で導入済みとは仮定しない。

## 古い構造を削除する条件

日数だけで判断しない。次をすべて満たしてから、独立した変更として削除する。

- 新構造への移行・件数・内容・継続する書き込みの整合性を確認した。
- 古い版の操作をAPI等で確実に止められる、または旧版の利用が終わった根拠がある。
- 実際の授業で1回以上利用し、目安として1週間ほど正常動作を確認した。1週間で自動的に安全になるわけではない。
- 旧アプリへ戻す必要がなく、復旧先も新しい構造と互換性がある。
- バックアップ・復旧方法と削除対象を明確にし、依頼の範囲で実施する。

実データ自体の削除は、互換用の列やコードの削除とは別判断とする。

## 復旧と注意事項

UIだけなら記録した直前のPages成果物へ戻す。DBを変更した場合、UIを戻すだけでは復旧しないことがある。API・DB・アプリの互換性を確認して戻す。共有API・DBの障害はデモにも本番にも影響する。

この公開リポジトリはPWA専用。API・管理室・DB移行の実装と秘密情報は管理側ワークスペースで管理する。運用が変わったらこの文書を更新し、AGENTS.mdとCLAUDE.mdのリンクが有効であることを確認する。
